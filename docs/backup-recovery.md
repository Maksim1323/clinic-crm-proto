# Шифрованная копия CRM и тренировочное восстановление

Только синтетические данные. Это ручной инструмент для проверки процесса, **автоматическое расписание и внешнее хранилище не настроены**. Не выполняйте восстановление поверх существующей базы. Код не удаляет и не меняет источник: копия читается согласованной PostgreSQL-транзакцией с проверкой совпадения `clinic_state` и `crm_v2`. Если зеркало не согласовано, создание копии останавливается. Это копия текущего состояния приложения, а не полный `pg_dump`: роли, разрешения PostgreSQL, расширения, другие таблицы/схемы, настройки Render и секреты окружения, история внешних систем и первоначальный снимок миграции в неё не входят. Максимальный размер расшифрованной копии — 128 МиБ, вся копия обрабатывается в памяти.

## Подготовка

В доверенной среде с Node/npm, доступом к источнику и установленными зависимостями задайте `DATABASE_URL` защищённым способом без печати в терминал/логи. Используйте отдельного оператора с минимально необходимыми правами на чтение. Подготовьте пути в защищённом постоянном хранилище **вне репозитория**, а ключ — в отдельном защищённом хранилище. Ни ключи, ни копии не добавлять в Git и не хранить вместе. `.gitignore` — только дополнительная страховка. `DATA_FILE` (локальный JSON без PostgreSQL) этим инструментом не копируется.

```sh
# Значения BACKUP_KEY_FILE и BACKUP_FILE — пути вне репозитория, не сами секреты.
node scripts/secure-backup.js keygen --key-file "$BACKUP_KEY_FILE"
node scripts/secure-backup.js backup --key-file "$BACKUP_KEY_FILE" --file "$BACKUP_FILE"
node scripts/secure-backup.js verify --key-file "$BACKUP_KEY_FILE" --file "$BACKUP_FILE"
```

`keygen` создаёт 32 случайных байта с правами 0600 и не перезаписывает существующий файл. Ключ обязателен для чтения, должен быть отдельным обычным файлом без прав группы/остальных; символическая ссылка отклоняется. Потеря ключа делает копию невосстановимой; протестируйте безопасное восстановление ключа, разграничьте и регулярно проверяйте доступ. Копия зашифрована AES-256-GCM с проверкой подлинности, файл создаётся с 0600 и без перезаписи. `verify` расшифровывает в памяти, проверяет аутентичность, версию и структуру, выводит дату и счётчики, но не записи. Проверка аутентичности не гарантирует полноту копии или будущую совместимость приложения.

Скопируйте зашифрованный файл в **независимое** защищённое хранилище (не в ту же БД, не на эфемерный диск Render), настройте ограничение доступа, мониторинг, контроль ошибок и периодические независимые проверки восстановления. Определите RPO/RTO, частоту, хранение поколений и сроки с владельцем данных и юристом. Никакой автоматический срок/удаление здесь не включены. Снимок `crm_v2.migration_backup` в исходной БД независимой копией не является.

## Тренировка восстановления в изолированную базу

Подготовьте **отдельную пустую тестовую PostgreSQL-базу** с именем, заканчивающимся на `_restore_test`, без рабочих подключений и только с синтетическими данными. Установите `TEST_RESTORE_DATABASE_URL` безопасно в доверенной среде. Команда отказывается работать с другим именем, любой непустой базой или существующей схемой `crm_v2`; она не удаляет таблицы и не перезаписывает их. Она создаёт таблицу состояния в тестовой базе, поэтому такая база после успеха уже не пустая:

```sh
node scripts/secure-backup.js restore-drill --key-file "$BACKUP_KEY_FILE" --file "$BACKUP_FILE"
```

В тренировочной копии старые сессии, предложения помощника и предварительные настройки очищаются, неотработанные задания автоматически помечаются завершёнными, а незавершённые отправки — неизвестными, чтобы случайно не повторить сообщения. Учётные записи и хеши паролей, карточки, переписка, задачи, журнал и настройки сохраняются. Это **намеренно не побитовое восстановление рабочего процесса**, и при реальном аварийном восстановлении потребуется отдельно согласовать состояние очереди, входов и отправок.

Чтобы проверить запуск восстановленного состояния, запускайте этот же выпуск приложения только на изолированной базе с `AI_AUTO_REPLY=false`, без токенов Telegram и ИИ, без публичного webhook/входящего трафика. Выполните вход тестовым сотрудником (старые сессии не работают), проверьте карточки, диалоги, задачи, счётчики и аудит. После проверки ответственный должен безопасно удалить изолированную среду по согласованному регламенту. Не перенаправляйте рабочий сервис и реальных пользователей на тренировочную базу. Запишите дату/версию, время восстановления, результат и обнаруженные проблемы без содержимого карточек.

Подтверждён локальный автоматический тест с двумя выделенными PostgreSQL-базами: копия, восстановление в пустую изолированную базу, запуск приложения, вход и сохранность синтетических данных; повторное восстановление в непустую базу отклоняется. На Render или с реальной базой и внешним хранилищем эта проверка не проводилась. Для полноценного аварийного восстановления в рабочую среду нужны отдельный согласованный runbook, тесты текущей версии, роли и процедуры БД, восстановление окружения и ключей, сверка после восстановления и решение о переключении; предоставленная команда намеренно этого не выполняет.

Автотест `tests/security-backup-postgres.test.cjs` использует `TEST_SECURITY_DATABASE_URL` и `TEST_SECURITY_RESTORE_DATABASE_URL` и **сбрасывает состояние обеих указанных баз** перед испытанием. Указывайте только две отдельные локальные одноразовые тестовые базы, никогда не Render/рабочую. Тестовые сбросы не запускаются при обычном создании или восстановлении копии.
